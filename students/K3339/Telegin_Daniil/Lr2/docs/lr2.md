# Потоки, процессы и асинхронность

## Цель работы

Реализовать и сопоставить подходы `threading`, `multiprocessing` и `asyncio`
для вычислительной и сетевой задач, измерить время выполнения и объяснить
получившиеся различия.

## Подготовка

Из папки `Lr2` создаётся виртуальное окружение и устанавливаются зависимости:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Для второй задачи используется PostgreSQL из ЛР1. Перед запуском нужно поднять
контейнер БД из папки ЛР1 и при необходимости передать `DATABASE_URL` через
переменную окружения. При первом запуске ЛР2 автоматически создаёт таблицу
`parsed_page`:

| Поле | Назначение |
| --- | --- |
| `id` | первичный ключ результата |
| `url` | адрес обработанной страницы |
| `title` | заголовок из тега `<title>` |
| `approach` | `threading`, `multiprocessing` или `asyncio` |
| `status_code` | HTTP-статус успешного ответа |
| `parsed_at` | время сохранения результата |

## Задача 1. Вычисление суммы

Все реализации делят диапазон `1…10^13` на равные непересекающиеся части. В
каждом модуле определена функция `calculate_sum(start, end)`, возвращающая сумму
одной части. Итог собирается из частичных сумм и сверяется с формулой
`n × (n + 1) / 2`.

Для выполнимости задания на исходной верхней границе внутри каждой подзадачи
используется арифметическая формула суммы диапазона. Это сохраняет требуемое
разбиение работы и даёт точный результат без многосуточного последовательного
цикла. Следствие важно для интерпретации: замер в этой задаче главным образом
показывает накладные расходы механизмов координации, а не ускорение тяжёлой
CPU-нагрузки.

### Threading

`task1_sum/threading_sum.py` запускает поток для каждого поддиапазона. Потоки
передают частичные суммы в `queue.Queue`, после чего основной поток объединяет
результаты.

```powershell
python -m task1_sum.threading_sum --workers 4 --save
```

### Multiprocessing

`task1_sum/multiprocessing_sum.py` использует `multiprocessing.Pool` и
`starmap`. Каждая часть обрабатывается отдельным процессом; вариант подходит для
реальных CPU-bound вычислений, поскольку процессы не разделяют GIL.

```powershell
python -m task1_sum.multiprocessing_sum --workers 4 --save
```

### Asyncio

`task1_sum/asyncio_sum.py` запускает корутины через `asyncio.gather`. Здесь нет
операций ожидания ввода-вывода, поэтому корутины не дают вычислительного
параллелизма и нужны для демонстрации отличия асинхронности от процессов.

```powershell
python -m task1_sum.asyncio_sum --workers 4 --save
```

Для одинакового запуска всех трёх вариантов используется:

```powershell
python -m task1_sum.benchmark --workers 4 --repeats 3
```

Результаты записываются в `results/task1_results.csv`.

## Задача 2. Параллельный парсинг и сохранение в БД

В `task2_parser/common.py` задан единый набор URL. Каждый вариант содержит
`parse_and_save(url)`: страница запрашивается, из HTML извлекается `<title>`, а
успешный результат сохраняется в `parsed_page`. Ошибки запроса или сохранения
фиксируются в консоли и не прерывают остальные URL.

### Threading

`threading_parser.py` делит URL на равные группы и запускает потоки. Подход
хорошо скрывает ожидание сетевых ответов, поскольку на время `requests.get`
GIL не удерживается.

### Multiprocessing

`multiprocessing_parser.py` передаёт равные группы URL независимым процессам.
Каждый процесс создаёт собственные HTTP-соединения и сессии БД. Это работает,
но запуск процессов обычно создаёт лишние накладные расходы для I/O-задачи.

### Asyncio

`asyncio_parser.py` использует `aiohttp.ClientSession` и `asyncio.gather`.
Сетевое ожидание не блокирует цикл событий; синхронная запись SQLModel вынесена
в `asyncio.to_thread`, чтобы не остановить остальные корутины.

Общий запуск:

```powershell
python -m task2_parser.benchmark --workers 4 --repeats 3
```

Результаты записываются в `results/task2_results.csv`.

## Методика измерений

Для каждого подхода надо использовать одинаковые число воркеров, верхнюю границу
и набор URL. Каждый эксперимент выполняется минимум три раза. Время измеряется
`time.perf_counter()` от запуска воркеров до завершения всех вычислений или
сохранений. В итоговую таблицу переносится среднее значение трёх запусков.

Перед повторным измерением второй задачи желательно удалить только тестовые
строки `parsed_page` или сохранить номер запуска отдельно, чтобы размер таблицы
не влиял на сравнение.

## Вывод

- Для CPU-bound задач процессы обычно предпочтительнее потоков из-за GIL.
  В данной реализации постоянная формула делает заметнее цену запуска воркеров,
  поэтому прямое сравнение времени не следует выдавать за оценку CPU-масштаба.
- Для I/O-bound парсинга `threading` и `asyncio` позволяют выполнять запросы
  во время ожидания ответов. `asyncio` особенно удобно при большом числе URL,
  когда важно не создавать поток на каждый запрос.
- Процессы полезны для CPU-нагрузки, но часто избыточны для обычного сетевого
  парсинга из-за накладных расходов на создание процессов и обмен данными.
